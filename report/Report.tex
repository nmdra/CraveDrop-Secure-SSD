\section{Executive summary}
This report documents a security assessment of CraveDrop, a food-ordering and delivery microservice application. The team preserved the vulnerable application at immutable tag \texttt{baseline-vulnerable}. The tag resolves to upstream commit \texttt{cb68a377f5b8cdc3b12f86883ac6fb703ef5e405}.

The assessment reproduced, fixed, and regression-tested seven distinct weaknesses. The work also adds one WSO2 Identity Server customer-login feature. The feature uses OpenID Connect Authorization Code flow with S256 PKCE and a CraveDrop HttpOnly cookie session. It is a feature, not an eighth counted vulnerability.

All tests use synthetic fixtures. Evidence files contain redacted request and response data only. The detailed evidence index is \texttt{docs/finding-matrix.md}.

\section{Project eligibility and method}
The original project is \href{https://github.com/nmdra/CraveDrop}{nmdra/CraveDrop}. It is an MIT-licensed food-ordering and delivery application. The selected default-branch baseline is dated 17 July 2025. The assessed work predates the July 2026 semester start.

The method used a fixed baseline, deterministic Customer A and Customer B fixtures, live baseline requests, focused code changes, and negative plus positive regression controls. A finding was counted only when it had a distinct root cause, a baseline attack, an impact, a focused fix, a blocked attack, an authorized control, and a residual-risk statement.

\section{System and trust boundaries}
CraveDrop uses separate user, order, payment, delivery, and driver services. The API gateway routes browser requests to these services. The services use PostgreSQL or MongoDB, depending on the service. The security fixes enforce identity and authorization at the affected service boundary. The gateway is not treated as the only authorization control.

\finding{V1: Missing authentication on payment actions}
\textbf{Baseline attack.} An anonymous request to \texttt{POST /api/payments/create-payment-intent} reached the payment handler. It did not receive an authentication error.

\textbf{Impact.} An attacker can invoke a payment action without a customer identity. This can consume payment-provider resources and bypass the intended customer boundary.

\textbf{Fix and result.} Payment routes now require a verified Bearer JWT. The caller identity comes from the verified token. The anonymous request returns 401. An authenticated synthetic customer reaches the payment-start handler.

\textbf{Residual risk.} The local control reaches a synthetic Stripe error. It does not prove a real card charge.

\finding{V2: Order IDOR or BOLA}
\textbf{Baseline attack.} An unauthenticated request read Customer A's synthetic order by order ID.

\textbf{Impact.} An attacker can view or alter another customer's order if the order ID is known.

\textbf{Fix and result.} Order reads and mutations require an authenticated customer. The query includes both order ID and verified customer ID. Customer B receives 404 for Customer A's order. Customer A can read the owned order.

\textbf{Residual risk.} Every new order route must apply the same ownership scope.

\finding{V3: Order mass assignment}
\textbf{Baseline attack.} An unauthenticated order update supplied \texttt{userId}, \texttt{totalAmount}, \texttt{status}, and \texttt{createdAt}. The service persisted client-controlled values.

\textbf{Impact.} A caller can alter ownership, price, lifecycle state, or audit data.

\textbf{Fix and result.} The controller rejects protected fields and allow-lists customer-editable values. The server owns identity, price, payment state, and timestamps. Protected fields return 400. Valid authorized updates and order creation succeed.

\textbf{Residual risk.} New editable fields require explicit review before they join the allow-list.

\finding{V4: Unauthorized delivery mutation}
\textbf{Baseline attack.} An anonymous caller changed a delivery status. The same boundary accepted a location update.

\textbf{Impact.} An attacker can falsify delivery progress or tracking data.

\textbf{Fix and result.} Delivery writes require a valid driver JWT, an assigned-driver match, and an allow-listed state transition. Anonymous, customer, and unrelated-driver writes fail. The assigned driver can make the valid status and location updates. A reverse transition returns 409.

\textbf{Residual risk.} The fix does not prove the integrity or accuracy of the driver device and GPS source.

\finding{V5: Broken administrative authorization}
\textbf{Baseline attack.} An unauthenticated request changed Driver B's availability through Driver B's ID.

\textbf{Impact.} An attacker can disrupt delivery allocation.

\textbf{Fix and result.} Driver availability updates require a verified driver JWT. The verified driver ID must match the URL ID. A driver cannot update another driver's availability. A driver can update own availability.

\textbf{Residual risk.} This finding covers driver availability. Restaurant administration remains outside this counted fix.

\finding{V6: Payment amount and state manipulation}
\textbf{Baseline attack.} A client created a card order with amount 1 instead of the fixture total 2500. The order was also marked paid.

\textbf{Impact.} A customer can lower the charge or obtain a paid order without confirmed payment.

\textbf{Fix and result.} The order service calculates the USD price from trusted product data. It ignores client currency and paid-status fields. New card orders start pending. A tampered request persists 2500 USD and pending status.

\textbf{Residual risk.} Payment confirmation must remain bound to a trusted order and verified provider event.

\finding{V7: Sensitive token exposure and session design}
\textbf{Baseline attack.} Login and refresh responses returned bearer tokens in JSON. The service logged refresh-token data. The frontend stored access tokens.

\textbf{Impact.} Script injection, browser access, or log access can expose bearer tokens and allow session impersonation.

\textbf{Fix and result.} Login and refresh issue strict HttpOnly cookies. The frontend does not store bearer tokens. Logging omits request query values, which also prevents OIDC authorization-code logging. Login and refresh JSON omit access tokens. Cookie mutations require the approved Origin.

\textbf{Residual risk.} XSS can still make same-origin requests while a user session exists. Future work includes Content Security Policy and broader XSS review.

\section{WSO2 OpenID Connect customer login}
The added feature supports one customer login with WSO2 Identity Server 7.1.0. CraveDrop generates state, nonce, and a PKCE verifier. It uses an S256 challenge and stores the temporary flow in a signed short-lived HttpOnly cookie. The callback exchanges the authorization code server-side and validates issuer, audience, RS256 signature, expiry, nonce, and subject.

The local account key is provider issuer plus subject. The service does not link a local account by matching email address. If the local provider does not release a verified email claim, the service stores a deterministic non-deliverable identity placeholder. The real synthetic-user control returned a safe dashboard redirect, issued strict HttpOnly CraveDrop cookies, cleared the flow cookie, and authorized a protected endpoint. Node 20 mocked controls reject tampered state before code exchange and reject invalid nonce or ID-token input.

\section{Supporting tools and secure development}
The team ran \texttt{npm audit} for user, order, payment, delivery, and driver services. The results are recorded in \texttt{evidence/tools/npm-audit.txt}. These dependency advisories are not counted vulnerabilities because the team did not reproduce an endpoint impact.

The OWASP ZAP local-gateway scan is deferred because its Docker image download and scan exceed the available bandwidth. No ZAP warning or scan result is claimed. The team must run a bounded scan before submission if bandwidth is available.

Preventive practices include dependency review, server-owned sensitive state, explicit field allow-lists, endpoint-level authorization, redacted evidence, synthetic data, focused negative and positive tests, and protected browser sessions.

\section{Conclusion}
The assessment preserves a reproducible vulnerable baseline and demonstrates seven distinct fixed vulnerabilities. The application now enforces authentication, ownership, server-owned payment state, delivery authorization, and cookie-session handling at the affected boundaries. A secure WSO2 customer-login path is available for local demonstration. Remaining risks and the deferred ZAP scan are stated without unsupported claims.
